# OPC UA переподключается внутри процесса, а не завершает процесс

## Контекст

Воркер OPC UA (`backend/app/services/opcua_service.py`) при накоплении ошибок
соединения вызывал `os._exit(1)` с комментарием «launcher перезапустит».
Комментарий оказался неверным для заводской поставки: `EkranchikServer.exe`
запускает backend дочерним процессом, а на его `Exited` вызывает `Fail()` и
`Shutdown()`, то есть сам завершается. Автозапуск — только
`HKCU\Software\Microsoft\Windows\CurrentVersion\Run` при входе пользователя,
это не служба и не supervisor. После `os._exit` заводской сервер оставался
лежать до ручного запуска или следующего входа в Windows.

В Docker-проде контейнер поднимает `restart: always`, но это свойство
конкретной среды, а не приложения. В dev `concurrently` после падения backend
тоже не перезапускает.

## Решение

Процесс не завершается по счётчику ошибок. Воркер сам восстанавливает связь:

- на каждую попытку создаётся новый клиент, прежний закрывается в `finally`;
- пауза между попытками — 1 → 2 → 5 → 10 с, дальше потолок 10 с;
- `consecutive_errors` считает подряд идущие ошибки соединения, сбрасывается
  при успешном `connect` и успешном опросе;
- счётчик используется только для `logger.error` на пороге и для статуса,
  а не для выхода;
- ошибка одной пачки чтения не считается ошибкой соединения и не приближает
  переподключение.

Попытка подключения ограничена по времени: `Client(url=..., timeout=10)` и
`asyncio.wait_for(client.connect(), timeout=20.0)`. Поэтому backoff всегда
наступает, даже если сеть зависла. Отдельная правка для этого не нужна —
подтверждено по коду 09.11.2026.

## Альтернативы

- **Оставить `os._exit` и научить launcher перезапускать backend.** Это
  отдельная задача про службу/supervisor и другую поставку; в текущем
  launcher перезапуска нет, а без него выход только ухудшает ситуацию.
- **Не закрывать старый клиент при реконнекте.** На OMRON остаются
  зомби-сессии; следующая попытка упирается в `BadTooManySessions`.
- **Фиксированные паузы по 10–20 с, как раньше.** Медленнее восстанавливаются
  короткие обрывы и не видно накопления ошибок.

## Последствия

- При обрыве связи сервер остаётся живым и возвращается к опросу сам.
- Если воркер всё же зависнет, автоматического перезапуска на заводской
  Windows-машине нет. Это ограничение поставки, а не следствие отказа от
  `os._exit`; supervisor остаётся отдельной задачей.
- В `/api/opcua/status` в `stats` появился `consecutive_errors`; по нему видно
  текущее состояние связи.
- Поведение закрыто `backend/tests/unit/test_opcua_service_reconnect.py`;
  сценарий обрыва проверен на локальном OPC UA сервере: воркер переподключился,
  процесс остался жив.
