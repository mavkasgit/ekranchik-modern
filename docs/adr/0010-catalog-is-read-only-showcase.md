# Каталог — витрина: артикул приходит извне, локальны только примечания

Спека: [0002](../specs/0002-catalog.md). Тикеты: 0015–0020.
Внешняя задача: T-377 в ktm2000.

## Контекст

Каталог KTM — источник данных артикулов: скрипт синка переносит длину,
количество на подвесе и фото. Киоск при этом оставался полноценным
редактором: создавал артикулы, менял любые поля, удалял их, загружал и
кропил фото. Два владельца одного поля давали ровно то, что дают всегда:
оператор исправлял норму, синк её откатывал; загруженное фото жило до первого
изменения исходника; удалённый артикул возвращался следующим запуском.
Добавить сюда ещё и ZIP-экспорт значило поддерживать третий, никем не
используемый путь данных.

Каталог в киоске решает одну задачу: показать на линии, что за артикул и как
он выглядит. Редактирование артикула — работа администратора в KTM, а не
оператора у конвейера.

## Решение

Каталог — **витрина**. Единственный владелец полей артикула — внешний
каталог: артикул, наименование, длина, количество на подвесе, фото и версии
файлов. Киоск хранит и редактирует только **примечание** — оно локальное, не
синхронизируется и переживает любой запуск синка.

Следствия решения:

- Из API уходят создание, правка, удаление, загрузка и удаление фото, кроп
  превью и ZIP-экспорт. Остаются чтение и `PATCH /notes`.
- В интерфейсе нет кнопок создания и удаления, загрузки и кропа, нет
  заблокированных полей: данные показываются текстом.
- Примечание сохраняется автоматически по потере фокуса. Кнопки «Сохранить»
  и проверки несохранённых правок нет: редактируется одно поле.
- Понятия «неактивный артикул» в витрине нет: все артикулы активны. Скрытие
  артикула — действие в источнике, а не флаг в киоске.
- Поиск, сортировка и фильтры считаются на клиенте по полному списку:
  пагинации и виртуализации нет, потолок — 1000 артикулов.
- Происхождение данных в интерфейсе не показывается: ни источника, ни даты,
  ни слова «синхронизация». Для оператора это готовая система; кто и когда её
  наполняет — внутреннее дело администратора.
- Свежесть данных обеспечивается ручным запуском синка. Плановая задача и
  индикатор устаревания в киоске не появляются.

## Альтернативы

- **Оставить двустороннюю правку и предупреждать «перезапишется».** Отвергнуто:
  предупреждение не спасает от потери правки, а объяснять оператору
  устройство синка на киоске бессмысленно.
- **Разделить поля на «из KTM» и «локальные» и разрешить править локальные.**
  Отвергнуто: единственное локальное поле, у которого нет пары в источнике, —
  примечание. Всё остальное имеет владельца, и второй редактор только создаёт
  расхождения.
- **Оставить ZIP-экспорт как резервную выгрузку.** Отвергнуто: каталог
  забирают синком, архив никто не использует; кнопка создавала впечатление,
  что витрину можно унести и восстановить из неё.
- **Показывать в футере «данные из KTM от <дата>».** Отвергнуто владельцем:
  интерфейс не должен объяснять, откуда берутся данные. Диагностика остаётся
  в логах и документации администратора.

## Последствия

- Оператор больше не может исправить фото или норму у линии: это делается в
  KTM и приезжает синком. Если синк не запускали, киоск показывает старые
  данные — это осознанный риск, он лечится процедурой, а не UI.
- Примечания — единственные локальные данные каталога. Их нужно включать в
  бэкап базы; синк их не восстанавливает.
- API каталога сокращается: `POST`, `PUT`, `DELETE`, загрузка фото и экспорт
  удаляются. Клиенты, которые ими пользовались, должны исчезнуть вместе с
  ними.
- `usage_count` остаётся мёртвой колонкой: она нигде не инкрементируется.
  Из ответа API её убираем, миграцию ради неё не делаем.
- Контракт синка расширяется: нужно переносить наименование и не фильтровать
  артикулы по активности. Это задача в ktm2000 (T-377).
- Поддержка обязана знать, что данные приходят синком, хотя интерфейс об этом
  молчит: иначе первый вопрос «почему тут старый артикул» уйдёт не туда.
