# Фото профиля на дашборде: артикул в ячейке книги

Спека каталога: [0002](specs/0002-catalog.md). Решение: [ADR 0011](adr/0011-photo-matching-by-article.md).
Инструмент проверки: [`scripts/photo-match-report.py`](../scripts/photo-match-report.py).

## Коротко

Дашборд показывает фото рядом с Профилем. Фото берётся из каталога, а Профиль —
из ячейки книги учёта как есть. Оператор пишет в эту ячейку не только артикул,
но и размер или пометку:

| Ячейка книги         | Артикул каталога |
| -------------------- | ---------------- |
| `ЮП-2083 2,75 метра` | `ЮП-2083`        |
| `ЮП-2083 (1.8)`      | `ЮП-2083`        |
| `ЮП-1880 2.5м`       | `ЮП-1880`        |
| `ЮП-2900 окно (381)` | `ЮП-2900`        |
| `ПТ-100 2.5м`        | `ПТ100`          |
| `Кр.труба 10мм`      | `Кр.труба 10мм`  |

Каталог хранит артикул без хвоста. Поиск фото сравнивал ячейку целиком, поэтому
у строк с размером снимок не находился: на дашборде была серая заглушка, а
подпись показывала всю ячейку. Сама строка при этом на экране была — пропадало
только фото.

## Правило поиска

`parse_profile` убирает из ячейки **обработки** («окно», «греб», «сверло»,
«фреза», «паз», «отв») и **длину в метрах** (`2,75 метра`, `(1.8)`, `3м`), но не
миллиметры и не размеры (`Кр.труба 10мм`, `1500х3000х2.0`): цифры такого вида
остаются частью артикула. «Срезать всё после пробела» нельзя: чистый артикул
может сам содержать пробелы, цифры и дефисы (`Кр.труба 10мм`, `ЮП-2464-1`),
а несколько артикулов через пробел — дефект книги, а не правило имени. Поэтому
разбор ячейки остаётся точным, а запасной путь появляется только в поиске фото:

1. точное совпадение имени;
2. нормализованное (латиница ↔ кириллица);
3. префикс + цифры (`СРЛ80`);
4. только цифры — как и раньше, с защитой от неоднозначности;
5. **новое:** если ничего не нашлось — ведущее слово ячейки (артикул до первого
   пробела) теми же ступенями 1–4.

Запасной проход не выполняется, если полное имя нашлось. Поэтому
`Кр.труба 10мм` по-прежнему находится целиком, а не по слову `Кр.труба`.
Полное имя остаётся в `canonical_name` только как подпись, когда фото нет.

Один и тот же маппинг используют обе таблицы дашборда — очередь загрузки
(`GET /api/dashboard`) и выгрузка (`GET /api/dashboard/opcua-unload-matched`):
`_build_profiles_info` в `app/api/routes/dashboard.py` зовёт
`catalog_service.get_profiles_photos_batch`.

## Длина профиля

Длина пишется в той же ячейке, что и артикул: `ЮП-2083 2,75 метра`,
`ЮП-2083 (1.8)`, `ЮП-1880 2.5м`. Это **отдельный признак** строки, а не часть
артикула (ADR [0012](adr/0012-profile-length-is-separate-annotation.md)):
`parse_profile` выносит её в `length_m`/`length_text` и убирает из имени,
поэтому подпись Профиля становится артикулом, а длина показывается бейджем.

Форматы, которые книга реально пишет (замер 18.11.2026):

| Как записано         | Строк | Бейдж  |
| -------------------- | ----: | ------ |
| `ЮП-1880 2.5м`       |    47 | 2,5 м  |
| `ЮП-2083 (1.8)`      |    30 | 1,8 м  |
| `2525 2.7м`          |    14 | 2,7 м  |
| `ЮП-1401 (3.05м)`    |    14 | 3,05 м |
| `Лайн 3,0м`          |    12 | 3 м    |
| `2626(2.7м)`         |    11 | 2,7 м  |
| `ЮП-2083 1.8м`       |    11 | 1,8 м  |
| `Бинокль 3,0м`       |    11 | 3 м    |
| `ЮП-2083 2,75 метра` |    10 | 2,75 м |
| `юп-2083 2.75м`      |     9 | 2,75 м |

Правила разбора (`app/services/profile_name.py`):

1. **Сначала скобка:** `\(\s*(\d+[.,]\d+)\s*(?:м(?:етр(?:а|ов)?)?\.?)?\s*\)`.
   Дробная часть обязательна: `(381)` — номер или партия, а не метры.
2. **Затем число с единицей «м»:** `(?<![\d.,])(\d+(?:[.,]\d+)?)\s*м(?:етр(?:а|ов)?)?\.?(?![а-яa-z])`.
   Отрицательный просмотр `(?![а-яa-z])` не даёт зацепить «мм».
3. Найденный фрагмент удаляется из имени; пробелы и пустые скобки подчищаются.
4. `length_m` — метры числом, `length_text` — запись с запятой, без лишних
   нулей, с пробелом перед «м»: `2.5` → `2,5 м`, `3.00` → `3 м`,
   `3.05` → `3,05 м`.
5. `split_profiles` делит ячейку по `+`/`/` **до** разбора: в
   `ЮП-2083(1.8м)+ ЮП-4863` длина есть только у первого профиля.

**Что не длина и остаётся в артикуле:** миллиметры (`Кр.труба 10мм`,
`труба 45мм`, `600*1800мм`), размеры листов и панелей (`1500х3000х2.0`,
`0.8x1000x600`, `рейка 100х200`), скобка с целым числом (`ЮП-2900 (381)`),
голые числа без единицы и дефисные артикулы (`ЮП-2464-1`). Отчёт по книге
отдельно проверяет, что среди чисел с «м» не осталось неразобранных: на
замере их 0.

Как связана с фото: после очистки имени `ЮП-2083 2,75 метра` ищется по
`ЮП-2083` точным совпадением, запасной проход по ведущему слову остаётся для
прочих хвостов (`381 (ЮП-2900 окно)` → каталог `381`). Артикул, которого нет
в каталоге, и артикул без файла снимка остаются с заглушкой.

API: `ProfileInfo` (`app/schemas/profile.py`) отдаёт `length_m: float | null` и
`length_text: str | null` в обеих таблицах. `name` — сегмент ячейки как
записан (`parsed.raw`), `canonical_name` — артикул каталога. Каталожная длина
(`profiles.length`, мм) **не подставляется**: у `ЮП-2083` в каталоге 2700 мм,
а в книге 2,75 м или 1,8 м — это разные вещи, и выдуманное число хуже
отсутствующего.

Интерфейс: бейдж стоит в ячейке «Фото» второй строкой под артикулом, в одном
ряду с жёлтыми бейджами обработок. Цвет — indigo
(`bg-indigo-100 text-indigo-900 border-indigo-300`), текст бейджа —
`length_text`; `title`/`aria-label` — «Длина 2,75 м». Бейдж виден и у строки
без снимка (заглушка + артикул + бейдж), у каждого профиля свой: длинный
артикул усекается, бейдж остаётся в ячейке.

Замер по последним 10 000 строкам книги `Учет КПЗ 2026.xlsm` (13.07.26 —
18.11.26): **265–266 строк с длиной** (книга пополняется между прогонами),
**45 уникальных написаний, 0 неразобранных**.
Полные таблицы — блок «Длины» в отчёте
(`npm run report:photos -- --limit 10000 --json .scratch/photo-match-report.json`,
ключ `lengths`).

## Как повторить

```bash
# текущее состояние, отчёт в .scratch/photo-match-report.html
npm run report:photos

# сравнение с коммитом до правки + JSON для машинной сверки
npm run report:photos -- --limit 10000 --compare-ref bac166f --json .scratch/photo-match-report.json
```

Скрипт только читает книгу и базу; ничего не пишет в каталог и журнал. Строки
книги читаются один раз, оба прогона (текущий код и код из `--compare-ref`)
видят одни и те же данные. В отчёте: карточки «было/стало», добавления,
остаток без артикула, остаток без снимка и таблица всех профилей выборки с
поиском.

Ограничения инструмента:

- нужен доступ к книге учёта (та же шара, что у приложения);
- `--compare-ref` читает `backend/app/services/catalog_service.py` из git;
  коммит должен содержать `get_profiles_photos_batch`;
- отчёт в `.scratch/` не версионируется (`.scratch/` в `.gitignore`), числа
  этого замера зафиксированы в этом файле.
