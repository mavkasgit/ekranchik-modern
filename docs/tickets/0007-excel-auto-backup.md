# 0007 — Автобэкап книги учёта КПЗ

Задача: сервер сам делает резервную копию активной книги учёта
(`Учет КПЗ 2026.xlsm`) раз в 2 часа. Копия кладётся в отдельную папку,
названную по имени книги; если папки нет — создаётся. Старые копии удаляются
по ступенчатой политике. Это не журнал подвесов: журнал — история проходов,
здесь — снимок самого Excel-файла.

Схема повторяет уже сделанный в hrms автобэкап БД: фоновая задача в `lifespan`,
ротация сразу после создания копии. Отличие — здесь один файл вместо `pg_dump`,
нет БД, API и экрана настроек.

## Что должно получиться

- Раз в 2 часа появляется копия активной книги, даже если дашборд никто не
  открывал (фоновая задача, как у журнала подвесов).
- Папка: `<имя книги>_backup` (`Учет КПЗ 2026.xlsm` → `Учет КПЗ 2026_backup`).
- Если файл не менялся с прошлой копии — новая не создаётся.
- Хранение: 24 двухчасовые копии за последние 48 часов, 7 дневных за неделю,
  7 недельных за 7 недель, месячные — бессрочно.
- Ошибка копирования (шара отвалилась, файл занят) не роняет сервер: пишем в
  лог и пробуем снова.
- Никакого UI, API и кнопок «сделать бэкап сейчас» — только настройки в `.env`.

## Решения

### 1. Какая книга и куда копируем

Берём **активную книгу**, а не путь из конфигурации: `excel_service.current_path`.
Оператор может сменить книгу через «Ввести путь», и бэкап должен следовать за
ней, иначе копия делается не того файла.

- Корень: `EXCEL_BACKUP_ROOT`, если задан; иначе каталог активной книги.
- Папка: `<корень>/<имя книги без расширения>_backup`.
- Файл: `ГГГГ-ММ-ДД_ЧЧ-ММ_<имя книги><расширение>`, например
  `2026-11-07_14-00_Учет КПЗ 2026.xlsm`. Время — московское (процесс уже
  переводится на `Europe/Moscow` в `main.py`). Если копия с таким именем уже
  есть (рестарт/ручной запуск в ту же минуту), добавляется `-01`, `-02` перед
  расширением; существующий файл никогда не перезаписывается.
- Имя папки санитизируется: запрещённые в Windows символы `<>:"/\|?*` и
  управляющие заменяются на `_`, хвостовые точки/пробелы срезаются.
- Папка создаётся с `parents=True, exist_ok=True`.

**Где это на практике**

| Установка                     | Корень по умолчанию            | Куда попадёт копия                                 |
| ----------------------------- | ------------------------------ | -------------------------------------------------- |
| Прод-контейнер                | `/app/excel`                   | `/app/excel/Учет КПЗ 2026_backup/…`                |
| Сервер-exe (заводская машина) | каталог UNC-книги              | `\\172.17.11.7\Оператор\Учет КПЗ 2026_backup\…`    |
| Dev-стенд                     | `../journal-dev/excel-backups` | `journal-dev/excel-backups/Учет КПЗ 2026_backup/…` |

Dev-корень задаётся явно, потому что dev и прод смотрят на одну шару: без
этого оба писали бы копии в одну папку и дублировали файлы. Имя папки при
этом всё равно берётся из имени книги.

**Прод сейчас монтирует книгу read-only.** В `docker-compose.prod.yml` стоит
`excel:/app/excel:ro`, в CIFS — `ro,file_mode=0444,dir_mode=0555`, в
`mount_and_start.sh` — то же. Чтобы писать рядом с книгой, монтирование
переводится в `rw` (список правок ниже). Если шара не пускает на запись под
учёткой монтирования, есть вариант без правки прав: `EXCEL_BACKUP_ROOT=/app/journal`
(том уже существует и наружу не раздаётся); имя папки не меняется.

### 2. Расписание

- Настройка `EXCEL_BACKUP_INTERVAL_MINUTES`, по умолчанию `120`.
- Фоновая задача стартует в `lifespan` и останавливается при выключении.
- Внутри — цикл с шагом 30 секунд (как у `journal_writer`): проснулись,
  проверили `now >= next_run`, сделали попытку, назначили следующий запуск.
  Так рестарт и перевод часов не сбивают расписание.
- При старте — немедленная проверка: если книга менялась после последней
  копии, копия создаётся сразу (догоняем пропущенное за простой).
- Успех или пропуск «файл не менялся» → следующий запуск через 120 минут.
- Ошибка (книга недоступна, занята, нет прав) → повтор через 5 минут; лог
  пишется один раз на состояние, а не каждые 5 минут.
- Копирование — блокирующая операция с сетевой шарой, поэтому выполняется в
  `asyncio.to_thread`, чтобы не подвешивать API и WebSocket.

Отдельного «ровно в 00:00, 02:00…» нет: при 2-часовом шаге это ничего не
даёт, а после рестарта появляются пропуски.

### 3. Пропуск неизменившегося файла

Сравниваем источник с самой новой копией в папке:

- размер совпадает;
- `mtime` совпадает с точностью до 2 секунд (SMB/CIFS может округлять
  метку; `shutil.copy2` сохраняет `mtime`).

Если оба условия выполнены — копия не создаётся, в лог идёт строка «книга не
менялась», следующий запуск через 2 часа. Если `mtime` отличается — копируем,
даже если содержимое фактически то же (Excel мог перезаписать файл без
изменений). Это дешёвая и достаточная проверка; хешировать книгу каждые 2
часа не нужно.

Ограничение: две записи в одну и ту же секунду с тем же размером теоретически
можно не заметить. Для Excel-книги, которую сохраняет человек, это
несущественно.

### 4. Политика хранения

Читаю требование так: **7 дневных — по одной за каждый из последних 7 дней,
7 недельных — по одной за каждую из последних 7 недель, месячные — по одной
за каждый месяц, бессрочно.**

| Уровень     | Что храним                                                | Верхняя граница | Что удаляем                                            |
| ----------- | --------------------------------------------------------- | --------------- | ------------------------------------------------------ |
| Двухчасовой | Все копии не старше 48 часов                              | 24              | Всё, что старше 48 часов и не попало в нижние уровни   |
| Дневной     | Самая новая копия каждого дня за последние 7 дней         | 7               | Дни старше 7 дней, если не попали в недельный/месячный |
| Недельный   | Самая новая копия каждой ISO-недели за последние 7 недель | 7               | Недели старше 7 недель, если не попали в месячный      |
| Месячный    | Самая новая копия каждого месяца                          | бессрочно       | Никогда                                                |

Уровни пересекаются: копия за последние 2 суток одновременно является
дневной, а копия текущей недели — недельной. Это одна и та же копия, а не
дубль; поэтому фактически файлов меньше, чем 24 + 7 + 7 + месячные.

Алгоритм ротации (выполняется после каждой попытки и при старте):

1. Собрать в папке только свои файлы: имя начинается с
   `<ГГГГ-ММ-ДД_ЧЧ-ММ>_<имя книги><расширение>` (возможен суффикс `-01`,
   `-02` при совпадении минуты). Чужие файлы, `.tmp`, копии других книг не
   трогаем.
2. Отсортировать по времени из имени, новые сверху.
3. Собрать `keep`:
   - 24 новейших файла не старше 48 часов;
   - по одному новейшему файлу на каждый из последних 7 календарных дней;
   - по одному новейшему файлу на каждую из последних 7 ISO-недель;
   - по одному новейшему файлу на каждый календарный месяц (все месяцы, без
     ограничения срока).
4. Удалить всё, что не попало в `keep`.
5. Каждое удаление — строкой в лог (как в журнале подвесов): файл, исчезнувший
   без следа, неотличим от файла, которого не было.

Ротация запускается после каждого тика, в том числе после пропуска: это
недорого (сотни файлов), зато лимиты соблюдаются и после простоя, и после
ручного добавления файлов. Отдельного «удалять раз в день / раз в неделю» нет:
при двухчасовом шаге это те же самые лимиты, только с задержкой.

### 5. Копирование и целостность

- Перед копированием проверяем, что книга «успокоилась»: два `stat` с паузой
  ~1 секунда; если размер или `mtime` изменились — откладываем попытку на 5
  минут, чтобы не поймать недописанный файл.
- Копируем в скрытый `.tmp` в той же папке, затем `os.replace` в итоговое имя.
  Неудачная копия не оставляет файл, похожий на настоящую резервную копию.
- При `PermissionError`/`OSError` (файл занят Excel, шара недоступна) — 3
  попытки с паузой 5 секунд, затем ошибка в лог и повтор через 5 минут.
- Временный файл удаляется при любой ошибке.

### 6. Настройки

| Переменная                      | По умолчанию | Назначение                                          |
| ------------------------------- | ------------ | --------------------------------------------------- |
| `EXCEL_BACKUP_ENABLED`          | `true`       | Включает фоновую задачу                             |
| `EXCEL_BACKUP_INTERVAL_MINUTES` | `120`        | Интервал между попытками                            |
| `EXCEL_BACKUP_ROOT`             | пусто        | Корень папок бэкапа; пусто — каталог активной книги |

Числа политики хранения (24 / 48 ч / 7 дней / 7 недель / месячные) — константы
в модуле `excel_backup.py`, а не переменные окружения: политика зафиксирована
этим тикетом. Если понадобится менять — меняется код и тест, а не настройка,
которую никто не помнит.

## Правки по файлам

### Бэкенд

1. `backend/app/core/config.py` — добавить `EXCEL_BACKUP_ENABLED`,
   `EXCEL_BACKUP_INTERVAL_MINUTES`, `EXCEL_BACKUP_ROOT` рядом с `EXCEL_*` и
   комментарий, почему dev-корень отличается от прода.
2. `backend/app/services/excel_backup.py` — новый модуль:
   - константы `KEEP_2H = 24`, `KEEP_2H_HOURS = 48`, `KEEP_DAILY = 7`,
     `KEEP_WEEKLY = 7`; месячные копии бессрочны и отдельного лимита не имеют;
   - `backup_dir_for(book_path)` — папка по имени книги;
   - `is_unchanged(book_path, latest_backup)` — проверка размера и `mtime`;
   - `backup_once(now=None)` — одна попытка, возвращает результат
     (`created` / `skipped_unchanged` / `skipped_missing` / `failed`) для
     тестов и логов;
   - `prune(backup_dir, now=None)` — ротация и список удалённых файлов;
   - `run_forever()` — цикл, старт/повтор, `asyncio.to_thread`;
   - глобальный `excel_backup` для `main.py` и тестов.
3. `backend/app/main.py` — импорт, запуск задачи в `lifespan` после журнала
   подвесов, отмена в `shutdown` с `suppress(asyncio.CancelledError)`.
   При `EXCEL_BACKUP_ENABLED=false` — только строка в лог, задача не стартует.
4. `backend/tests/unit/test_excel_backup.py` — новые тесты (список ниже).
5. `backend/tests/conftest.py` — autouse-фикстура, которая выставляет
   `settings.EXCEL_BACKUP_ENABLED = False` на время тестов: иначе тест,
   открывший `TestClient` через `with`, может сделать реальную копию с боевой
   шары на машине разработчика.
6. `backend/.env.example` — документировать три переменные и dev-значение
   `EXCEL_BACKUP_ROOT`.
7. `backend/.env` — локально для dev:
   `EXCEL_BACKUP_ROOT=../journal-dev/excel-backups`. Файл отслеживается git,
   поэтому dev-значение коммитится; в контейнер оно не попадает — прод
   получает свой корень через `environment` в compose.

### Прод и монтирование

1. `infra/compose/docker-compose.prod.yml`:
   - `excel:/app/excel:rw` вместо `:ro`;
   - `o: ${EXCEL_VOL_OPTS:-bind,rw}` вместо `bind,ro`;
   - в `environment` добавить `EXCEL_BACKUP_ROOT=/app/excel`, чтобы dev-значение
     из `backend/.env` не переехало в контейнер.
2. `infra/compose/.env.example` и серверный `infra/compose/.env`: в
   `EXCEL_VOL_OPTS` заменить `ro` на `rw`, `file_mode=0444` на `0644`,
   `dir_mode=0555` на `0755`. Запись идёт только в `<книга>_backup/`, остальную
   шару приложение по-прежнему только читает. `infra/compose/.env` в git не
   хранится (там пароль от шары): на сервере его правят при деплое вручную.
3. `infra/mount_and_start.sh` — те же `rw`/`0644`/`0755` в `MOUNT_OPTS` и
   `FSTAB_LINE` (скрипт перепишет `/etc/fstab`, если строка отличается).
   На сервере и `.env`, и fstab обновляются при деплое вручную: скрипт
   запускается человеком, git их не доставляет.
4. `README.md` — обновить абзац про `:ro` и добавить короткий раздел про
   автобэкап и его настройки.

## Тесты

Все — на `tmp_path` и фейковом `.xlsm`, без реального Excel и без сети.

1. Создаётся папка `<имя>_backup`, в ней копия с тем же содержимым; `mtime`
   источника сохранён.
2. Повторный запуск без изменения источника — второй копии нет, результат
   `skipped_unchanged`.
3. После изменения содержимого/`mtime` — вторая копия появляется.
4. Нет исходного файла — папка не создаётся, результат `skipped_missing`.
5. `EXCEL_BACKUP_ROOT` задан — папка создаётся внутри него, а не рядом с книгой.
6. Имя книги с недопустимыми для Windows символами — папка получает
   безопасное имя.
7. Ошибка копирования — `.tmp` удалён, итогового файла нет, результат
   `failed`.
8. Ротация двухчасового уровня: 30 файлов за 60 часов → остаются 24 новейших
   в пределах 48 часов; более старые удалены, если не являются дневным,
   недельным или месячным представителем.
9. Дневной уровень: файлы за 10 дней → по одному (самому новому) за каждый из
   последних 7 дней.
10. Недельный уровень: файлы за 10 недель → по одному за каждую из последних
    7 ISO-недель.
11. Месячный уровень: файлы за 14 месяцев → по одному за каждый месяц,
    старые месяцы не удалены.
12. Чужие файлы (`notes.txt`, копия другой книги, `.tmp`) не удаляются.
13. Совпадение минуты: вторая копия получает суффикс `-01`, первая не
    перезаписывается.
14. `run_forever` делает попытку сразу при старте и не чаще интервала
    (интервал в тесте — секунды, `backup_once` подменён).

   `journal-dev/excel-backups/Учет КПЗ 2026_backup/` — там одна копия.
2. Временно поставить `EXCEL_BACKUP_INTERVAL_MINUTES=1`, сохранить книгу —
   появляется вторая копия; не менять книгу — в логе «не менялась», новой

3. Смоделировать старые файлы с датами в именах и убедиться, что после тика
   остались 24 двухчасовых, по одной дневной/недельной/месячной копии.

Прод:

1. Обновить `infra/compose/.env` и прогнать `infra/mount_and_start.sh` (или
   вручную поправить fstab), пересобрать бэкенд.
2. Проверить запись из контейнера:
   `docker exec ekranchik-backend-prod sh -c 'mkdir -p "/app/excel/Учет КПЗ 2026_backup" && touch "/app/excel/Учет КПЗ 2026_backup/.write-test"'`
   и удалить тестовый файл. Если `Permission denied` — включить вариант
   `EXCEL_BACKUP_ROOT=/app/journal` и не менять права шары.
3. Дождаться первого бэкапа (или временно поставить интервал 1 минуту),
   проверить файл на шаре с Windows и в
   `docker logs ekranchik-backend-prod`.
4. Перезапустить контейнер: при изменённой книге копия создаётся сразу, при
   неизменённой — пропуск с записью в лог.
5. Убедиться, что `ExcelWatcher` не реагирует на файлы внутри папки бэкапа:
   он смотрит каталог книги **не рекурсивно** и фильтрует по `.xlsx/.xls/.xlsm`,
   а копии лежат в подпапке.

## Риски и как снижаем

- **Шара не пускает на запись.** Главный риск: CIFS смонтирован с `guest` и
  `ro`. Сначала проверяем `touch` из контейнера; если нельзя — переключаемся
  на `EXCEL_BACKUP_ROOT=/app/journal` без правки прав шары.
- **Книга занята Excel.** Копирование только на чтение, Excel обычно не
  блокирует; при ошибке — 3 попытки и повтор через 5 минут.
- **Недописанный файл.** Проверка «два `stat` с паузой» и копия через `.tmp`.
- **Сеть тормозит.** Копия в отдельном потоке; API и WebSocket не ждут шару.
- **Рост папки.** Месячные копии не удаляются никогда: при книге 10 МБ это
  ~120 МБ в год, при 50 МБ — ~600 МБ в год. Место на шаре нужно держать в
  голове; отдельного алерта в этой задаче нет.
- **Дубли dev/прод.** Dev пишет в `journal-dev/excel-backups`, прод — рядом с
  книгой; на одной машине одновременно два сервера не запускаются.
- **Точность `mtime`.** Сравнение с допуском 2 секунды; редкий пропуск
  одинаковых по размеру сохранений в одну секунду считаем приемлемым.
- **Часовой пояс.** Имена файлов и даты ротации — по московскому времени,
  как и журнал; процесс уже выставляет `Europe/Moscow`.
