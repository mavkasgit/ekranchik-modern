# 0027 — Числовые коды профилей без ведущих нулей

Источник: строка книги №20 от 20.11.2026: в книге профиль `33`, в каталоге
`033`. KTM: [mavkasgit/ktm2000#444](https://github.com/mavkasgit/ktm2000/issues/444).

## Задача

Книга пишет профиль `33`, каталог знает `033` (KTM SKU `033`, «Стык с
дюбелем 40мм»). Сейчас дашборд не находит профиль: нет фото, карточка
`GET /api/catalog/33` отдаёт 404. В KTM импорт плана с артикулом `33` так же
не находит продукт `033`.

Синк KTM → Экранчик уже считает `033` и `33` одним кодом
(`ktm2000/scripts/sync-ekranchik.py`, `canon()`), а рантайм обеих систем —
нет. Нужно одно правило на всех.

## Правило

- Чисто числовой код (`33`, `033`) сравнивается по числу: `33 == 033`.
- Ведущие нули не значимы только у чисто цифровых кодов; `ЮП-033` и `033`
  остаются разными.
- Если в справочнике есть и `33`, и `033`, совпадение неоднозначно: не
  выбирать молча, оставить прежнее поведение (нет совпадения / отказ).
- Регистр, пробелы, дефисы и кириллица нормализуются как сейчас; точное
  совпадение всегда побеждает числовое.

## Объём

### Экранчик

- `CatalogService.get_profiles_photos_batch` (`backend/app/services/catalog_service.py`):
  добавить числовой ключ для чисто цифровых имён и учитывать уникальность.
  Если на числовой ключ приходится больше одного профиля, не матчить.
- `CatalogService.get_profile`: если точного имени нет, искать числовой
  эквивалент по тому же правилу уникальности. Нужно для
  `GET /api/catalog/{name}` и карточки профиля.
- `docs/photo-matching.md` (или `docs/specs/0002-catalog.md`): одна строка о
  числовых кодах и уникальности.

### KTM

- `backend/app/services/import_normalization.py`: числовой ключ для чисто
  цифровых SKU, использовать в `SkuEntry` / `match_sku_cell` и в импорте
  плана (`plan_import_service.py`). См. #444.
- Документация KTM: согласовать с `docs/catalog/packing-plan-2026-articles.md`
  (там `033 ↔ 33` при уникальности уже описано); пометка `033 ≠ 33` в
  `docs/catalog/kpz-hanger-norms.md` относится к raw-слою анализа.

### Тесты

- Экранчик: `33` находит `033`; `31` находит `31`; два профиля `33`/`033` —
  неоднозначность, без выбора; `ЮП-033` не путается; точное совпадение
  побеждает; неизвестный код остаётся без фото.
- KTM: `33` находит `033` в `match_sku_cell`/импорте; `031` ↔ `31`;
  `ЮП-033` не путается; два продукта `33`/`033` — `ambiguous`.

## Приёмка

1. Строка книги с `33` показывает фото и карточку профиля `033`; текст
   «Профиля» остаётся записью книги (`33`).
2. `GET /api/catalog/33` отдаёт профиль `033`.
3. Импорт плана KTM с `33` привязывается к продукту `033`.
4. Если существуют оба `33` и `033`, выбор не делается молча.
5. `npm run gate` в Экранчике и KTM зелёный; backend/frontend тесты зелёные.

## Ограничения

- Не переименовывать SKU и профили, не править данные БД.
- Не трогать нечисловые артикулы.
- KTM — источник; Экранчик только читает каталог.
