# 0006 - Смысл строки дашборда: правила в модуле, строка и ячейка адресуемы

Связанный тикет: [issue #13](https://github.com/mavkasgit/ekranchik-modern/issues/13).

## Проблема

Правила строки жили в разметке `DataTable`: `grid-row`, `grid-span` и классы
окраски вычислялись прямо в JSX, а сводка Excel и OPC UA собиралась внутри
`Dashboard` (`hangerMetaByNumber`). Проверить их можно было только рендером
всей страницы, а e2e искал `role="cell"`, которого в разметке не было.

## Решение

**`frontend/src/lib/domain/dashboardRow.ts`** - единственный владелец того,
что означает строка:

- `describeHangerRow(hanger, index, { profileOverflows })` - тон окраски
  (`defect` > `sticks` > `delayed` > `plain` с чередованием), бейджи (`DELAY`,
  `CYCLE_ERROR`, `DEFECT`; `NO_ROW` молчит - пустая строка читается сама), имя
  профиля («Клюшки» вместо пустого у клюшек, `+` разделяется пробелом), судьба
  колонки «Фото» и `rowSpan`:
  - снимки есть, профилей больше двух **или** текст профиля не влез в три
    строки - снимки уходят на второй ряд (`photosBelow`), а «Профиль» занимает
    треки `profile` + `photo`;
  - снимков нет ни одного - колонка «Фото» отдаётся профилю
    (`profileOwnsPhotoColumn`), заглушки не рисуются;
  - иначе снимок стоит в первой строке рядом с артикулом (1-2 профиля);
  - `profileOverflows` приходит замером из строки (`HangerRow`): длину текста в
    три строки знает только браузер, поэтому модуль принимает флаг, а не
    считает символы. Замер с защёлкой: расширили строку - она остаётся широкой
    до смены текста, иначе раскладка зацикливается;
- бейджи профиля (`ProfileBadges`) стоят сбоку от своего снимка, пока влезают в
  колонку, и только когда места нет совсем — под полосой снимка. Полоса — 40 px:
  пара кадров прижата к низу (общая линия), одиночный центрируется. Поэтому
  высота бейджа не меняет высоту снимка. Во втором ряду бейджи стоят справа от
  снимка;
- подпись снимка (`ProfilePhotoSlot`, `showName`) — артикул профиля у кадра —
  рисуется только когда снимков меньше, чем профилей: по ячейке «Профиль» с
  «3416 + 362» иначе не понять, чей это кадр. Когда кадр есть у каждого, порядок
  кадров совпадает с порядком артикулов и подпись не нужна — строка не растёт.
  Сама подпись садится сбоку от снимка, над бейджами; под кадр уходит только
  если сбоку места нет совсем;
- `isBlankRow(row)` - строка без времени, профиля и вида материала в боковую
  очередь не попадает;
- `mergeHangerMeta(rows, events)` - сводка по номеру подвеса, проход линии
  (OPC UA) главнее строки книги, пустые значения книги не стирают.

Правило закрыто `dashboardRow.test.ts` без рендера: `npx vitest run`.

**Разметка.** Grid-рисование осталось, но строка несёт `role="row"`, ячейки -
`role="cell"`, шапка - `role="columnheader"`, а таблица - `role="table"` с
именем («Очередь загрузки» / «Выгрузка»). Доступное имя ячейки - её текст,
поэтому `getByRole("cell", { name })` находит клиента, профиль и цвет книги.

**E2E `live_demo`.** Тест больше не зашивает номер подвеса и имена тестовых
строк: номер он читает с линии, а ожидаемые клиента, профиль и цвет берёт у
бэкенда (`/api/dashboard/opcua-unload-matched`) - и проверяет, что они стоят в
ячейках строки таблицы выгрузки. На стенде без книги значения - прочерки, и
тест это переживает.

**Временный стенд.** `VITE_API_TARGET` переключает прокси `/api`, `/ws` и
`/static` на другой порт: e2e можно прогнать на 8014/4174, не трогая рабочий
стенд на 8013/5173. По умолчанию цель та же.
